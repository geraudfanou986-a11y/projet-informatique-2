TP4 — Squelette technique, contrat d'API et ADR-001

Projet informatique 2 · L3 SIL · application Web de gestion des stages et des soutenances (données fictives).
Objectif du TP : mettre en place l'arborescence, la configuration et le premier point d'entrée. À remettre : squelette du projet, README, contrat des routes et ADR-001.

1. Squelette du projet et séparation des couches

TP4/
├── public/
│   └── index.php            point d'entrée unique, routage minimal, GET /api/sante
├── src/
│   ├── Controllers/         requête HTTP → réponse HTTP (aucun SQL, aucune règle métier)
│   ├── Services/            règles métier (aucun SQL, aucun HTTP)
│   └── Repositories/        seul endroit où du SQL est écrit, requêtes préparées
├── config/
│   ├── config.php           lecture du .env
│   └── database.php         fabrique PDO avec exceptions
├── tests/
│   └── test_connexion.php   test de connexion sans afficher le mot de passe
├── .env.example             valeurs factices versionnées
├── .gitignore               exclut .env, vendor/, *.log, sauvegardes
└── README.md                prérequis, installation, commandes

Le point d'entrée unique public/index.php lit la méthode et le chemin, puis appelle le contrôleur adapté. Aucun fichier PHP n'est accessible directement hors de public/.

Connexion PDO (exceptions activées)

return new PDO($dsn, $c['user'], $c['pass'], [
    PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION,
    PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC,
    PDO::ATTR_EMULATE_PREPARES => false,
]);
Secrets : le mot de passe est lu dans .env, fichier exclu par .gitignore. Seul .env.example est versionné, avec des valeurs fictives. Le test de connexion n'affiche jamais le mot de passe.

3. ADR-001 — Architecture monolithe modulaire PHP

ChampContenu
ContexteÉquipe de trois ou quatre étudiants, 25 heures, postes Windows, déploiement local sans infrastructure mutualisée.
DécisionMonolithe modulaire PHP 8 avec PDO, sans framework, organisé en public/, Controllers/, Services/, Repositories/ et config/.
MotifDémarrage rapide, aucune dépendance à installer, couches suffisantes pour séparer HTTP, règles métier et SQL.
Conséquence positiveDéploiement simple (copier le dossier) et compréhension du code par tous les membres.
Conséquence acceptéeRoutage et validation écrits à la main : ils devront être couverts par des tests (TP6) et le contrôle d'accès vérifié (TP8).
Critères d'évaluation : séparation des couches · secrets non versionnés · route de santé fonctionnelle.
